01 / ขอบเขตและหลักออกแบบ

Blueprint v2 • 8 ตุลาคม 2026 • XC X TK • เอกสารเสนอออกแบบจากแผนที่รวมไว้ในบทสนทนา ไม่ใช่รายงานตรวจ schema หรือ API ของ ZIP เดิม และยังไม่ได้เปลี่ยนระบบที่เผยแพร่แล้ว

ใช้ Admin / Desk / Kiosk เดิมเป็นจุดเริ่มต้นการพัฒนา แต่ชื่อ route และตารางในเอกสารนี้เป็นข้อเสนอ ต้องทำ mapping กับระบบเดิมก่อน migration เป้าหมายคือข้อมูลกลางที่เชื่อมแหล่งลูกค้า การจอง ธุรกรรม ค่าคอม โปรโมชั่น และสมาชิกได้ตลอดเส้นทาง

MVP: เว็บตอบสนองมือถือสำหรับลูกค้าและพันธมิตร, Desktop สำหรับทีมงาน, จอแนวนอนสำหรับหน้าเรท • การจองเริ่มด้วยจองคิว • ไม่รับชำระเงินออนไลน์ในขอบเขตนี้ • แอปติดตั้งและล็อกเรทอยู่ระยะถัดไป

02 / บทบาทและการเข้าถึง

บทบาทขอบเขตทำอะไรได้ข้อควบคุม
EXECUTIVEทุกสาขาตามองค์กรภาพรวม อนุมัติกรอบเรท/งบ/ข้อยกเว้นใช้ approval policy ตามประเภทและวงเงิน
ADMINองค์กร/สาขาตามสิทธิตั้งค่าระบบ ผู้ใช้ บทบาท สาขาไม่มีสิทธิอนุมัติเงินโดยอัตโนมัติ

BRANCH_MANAGERสาขาตนเองคิว เงินสด ส่งมอบและปิดกะข้อยกเว้นตาม approval policy
TELLERสาขาและกะที่เปิดตรวจลูกค้า รับจอง ทำรายการห้ามแก้รายการสำเร็จโดยตรง
FINANCEสาขาตามสิทธิกระทบยอด ต้นทุน ค่าคอม และจ่ายแยกผู้จัดทำ/อนุมัติ/จ่าย
MARKETINGข้อมูลที่จำเป็นต่อการตลาดร่างโปร กลุ่มลูกค้า วัดผลไม่เปิดสิทธิเอกสารยืนยันตัวตน
PARTNERบัญชีพันธมิตรตนเองส่งต่อ จอง ดูรายการและค่าคอมซ่อนข้อมูลส่วนบุคคลที่ไม่จำเป็น
CUSTOMERข้อมูลตนเองจอง ประวัติ สิทธิและ referralยืนยันบัญชีก่อนดูข้อมูลส่วนตัว

Server ตรวจทั้ง organization_id, branch scope และ owner ของข้อมูลทุก request; UI ซ่อนปุ่มอย่างเดียวไม่เพียงพอ Public display เปิดเฉพาะเรทเผยแพร่และข้อมูลสาขา ไม่เปิดยอดเงินสดหรือข้อมูลลูกค้า

05 / Rate Engine และการเผยแพร่

หัวข้อข้อกำหนด
นิยาม BUY / SELLBUY = ร้านซื้อเงินต่างประเทศจากลูกค้า; SELL = ร้านขายให้ลูกค้า แสดงคำอธิบายนี้บน Desk และแอปลูกค้า
หน่วยราคาTHB ต่อ unit_size ของสกุลต่างประเทศ; normalize จำนวน × rate ÷ unit_size เช่น 100 JPY ไม่เท่ากับ 1 JPY
ฐานอ้างอิงเก็บ buy_reference และ sell_reference แยก พร้อม source, effective_date, fetched_at, source unit; หากไม่มีข้อมูลฝั่งที่ต้องใช้ ให้ unavailable ห้ามเดา
สูตรเสนอauto_buy = base_buy × (1 + buy_adjust_pct/100); auto_sell = base_sell × (1 + sell_adjust_pct/100) ใช้เปอร์เซ็นต์มีเครื่องหมาย +/− และแสดง preview
manualoverride แยกรายฝั่ง: buy_mode / sell_mode = AUTO | MANUAL; ปุ่มปรับรวมข้ามฝั่ง MANUAL; กลับ AUTO ต้องยืนยันพร้อม preview
validationrate > 0; หลังปัดเศษ buy ≤ sell; ข้อมูลอ้างอิงต้องครบ; out-of-bound → approval; publication ทั้งชุดสำเร็จหรือไม่เปลี่ยนเลย
precisionDECIMAL เท่านั้น; proposed rate scale 8 / % scale 4; ปัดยอด THB 2 ตำแหน่ง HALF_UP ที่ยอดสุดท้าย; เงินต่างประเทศตาม minor unit; ห้าม JS float เป็น authoritative
versionทุก publication immutable; เปลี่ยน published pointer แบบ atomic; Desk quote อ้าง rate line id และ snapshot; การเผยแพร่ใหม่ไม่แก้ snapshot เก่า
refresh / staleความถี่ดึงข้อมูลและ cutoff ต้องตรวจแหล่ง ธปท. ก่อน build adapter; แสดง source date และ last fetched แยกกัน หาก stale ให้ใช้ policy จำกัด/หยุด quote ไม่อ้างว่าเป็น tick real time
MVPเรทแยกสาขาและสกุล รองรับ denomination group สำหรับธนบัตร; เริ่มจากกลุ่ม ALL เมื่อยังไม่มี pricing ตามขนาดธนบัตร

06 / Workflow และสถานะ

รายการสถานะและทางเดินกติกา
เรทDRAFT → PENDING_APPROVAL → APPROVED → PUBLISHED → SUPERSEDED; REJECTED กลับร่างใหม่MANUAL ทุกการเปลี่ยนมีเหตุผล; อนุมัติผูก version/hash; แก้แล้วต้องขอใหม่
QuoteACTIVE → ACCEPTED | EXPIRED | CANCELLEDindicative สำหรับจองคิว; binding สำหรับล็อกเรทในระยะ 6; quote ใหม่เมื่อเปลี่ยนจำนวน/สิทธิ
BookingPENDING_CUSTOMER_CONFIRMATION → CONFIRMED → CHECKED_IN → IN_SERVICE → COMPLETED; CANCELLED / NO_SHOW / EXPIREDลูกค้าจองเองเริ่ม CONFIRMED; partner จองต้องยืนยันลูกค้า; COMPLETED ได้เมื่อ transaction สำเร็จ
TransactionDRAFT → PENDING_APPROVAL (ถ้าจำเป็น) → CONFIRMED → COMPLETED; CANCELLED ก่อนสำเร็จCOMPLETED เมื่อ posting เงินและ inventory สำเร็จ atomic; แก้ผ่าน reversal/adjustment เอกสารใหม่เท่านั้น
ReversalREQUESTED → APPROVED → POSTED; REJECTEDเชื่อม original transaction; MVP ยกเลิกทั้งรายการ; partial reversal เป็นขอบเขตเพิ่มเติม
CommissionPENDING_REVIEW → APPROVED → PAYABLE → PAID; VOIDหลังจ่ายแล้วคืนรายการใช้ debit adjustment และ net batch ถัดไป ไม่ลบ PAID เดิม
CampaignDRAFT → SIMULATED → PENDING_APPROVAL → APPROVED → SCHEDULED → ACTIVE → PAUSED | EXPIREDแก้ rule ต้องสร้าง version ใหม่; งบ/จำนวนสิทธิ check และ reserve แบบ atomic
MemberCALCULATED → EFFECTIVE; เปลี่ยน tier ผ่าน historyรัน recalculation idempotent; reversal ปรับฐาน; tier สิทธิและช่วงมีผลต้องเก็บ version
Cash transferDRAFT → APPROVED → DISPATCHED → RECEIVED → RECONCILEDยอดอยู่ in-transit ระหว่างส่ง; ผู้รับรับรองยอดจริง; difference เป็น exception ไม่บังคับตรง

11 / นิยามตัวเลขบริหาร

ตัวชี้วัดนิยาม
ยอดซื้อ / ยอดขายTHB equivalent ของ completed lines แยก shop_side; แสดง gross และ reversal แยก; volume รวมไม่ใช่รายได้
ส่วนต่างรับรู้สำหรับขาย: เงิน THB รับ − allocated FX cost; สำหรับซื้อเงินต่างประเทศไม่รับรู้กำไรเพียงเทียบ BUY/SELL ปัจจุบัน; inventory ยังไม่ขายแสดง valuation แยก
Contributionส่วนต่างรับรู้ − commission expense − promo/reward expense ที่ไม่รวมอยู่ในเรทแล้ว; ห้ามหัก rate discount ซ้ำ
กำไรสุทธิต้องมีค่าใช้จ่ายอื่นและนโยบายบัญชีครบ; ก่อนครบให้ใช้ชื่อ contribution ไม่ตั้งชื่อ net profit
Booking conversioncompleted bookings ÷ confirmed bookings ใน cohort วันนัดเดียวกัน; รายการยังไม่ถึงวันนัดแยกออก
Partner conversionลูกค้าที่ attributed และมี completed transaction ÷ eligible referred customers ใน cohort ที่กำหนด
Repeat customerลูกค้าที่มี completed transaction ก่อนครั้งปัจจุบัน; ใช้ customer_id กลางทุกสาขา
RFM / valueRecency จาก completed ล่าสุด; Frequency จำนวนธุรกรรม; Value แสดงทั้งยอดและ realized contribution ตาม lookback
Campaign effectรายงาน observed attributed contribution; incremental lift ต้องมี baseline/กลุ่มเปรียบเทียบ ห้ามเรียกยอด attributed ว่ากำไรเพิ่มทั้งหมด
เงินพร้อมใช้งานon_hand − active reservations; เงิน in-transit แยก; cash variance = counted − expected
Data freshnessแสดง as_of แต่ละสาขาและ pending events; กรอง business date ตาม timezone สาขา

13 / Acceptance Criteria และลำดับส่งมอบ

ระยะตรวจรับได้เมื่อ
1 • เรทและหน้าร้านauto ปรับตาม % แบบมีเครื่องหมาย; manual แต่ละฝั่งคงเดิม; cross-unit คำนวณถูก; publication ทุกหน้าตรง; stale แสดงชัด; out-of-bound ไม่ publish ข้ามอนุมัติ
2 • ธุรกรรมและบริหารcomplete ซ้ำไม่เพิ่มยอด; concurrent exchange ไม่ใช้ stock เกิน; reversal กระทบยอดถูก; dashboard เจาะถึงต้นทางและตรง cash/ledger ตามนิยาม
3 • Partner / referralข้าม partner scope ไม่ได้; attribution หลักไม่ซ้ำ; reversal หลัง payout มี adjustment; retry payout ไม่จ่ายซ้ำ
4 • Bookingสองคนจอง slot สุดท้ายสำเร็จได้คนเดียว; partner confirmation ครบ; booking เชื่อม transaction; QR ไม่เปิด PII; เปลี่ยนเวลาไม่กิน slot สองครั้ง
5 • Marketing / memberงบและสิทธิสุดท้ายไม่ใช้เกิน; simulate ตรง quote จริง; rule version ย้อนตรวจได้; reversal ไม่ค้างสิทธิ; ถอน consent หยุด marketing eligibility
6 • Rate lock / appreservation expiry คืน stock; complete ใช้ quote lock ที่ถูกต้อง; network retry ไม่ซ้ำ; app อ่านข้อมูลชุดเดียวกับเว็บ

ก่อนเริ่มโค้ด: ทำ mapping route / entity / auth / cash workflow ของระบบเดิม → ยืนยันค่าธุรกิจจำเป็น → migration rehearsal ด้วยข้อมูลทดลอง → ทดสอบตามเกณฑ์ข้างต้น → pilot หนึ่งสาขา → ขยายสาขา เอกสารนี้พร้อมใช้เป็นกรอบแตกงาน แต่ยังไม่ใช่ physical SQL migration หรือ final UI
