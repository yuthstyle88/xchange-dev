01 · ขอบเขตและสถานะ

สถานะเปิดใช้งานและผลตรวจด้านล่างเป็นข้อมูลที่เจ้าของส่งมา เอกสารนี้ไม่ได้ตรวจระบบออนไลน์หรือซอร์สจริงซ้ำ ไม่ใช่คำรับรองว่าระบบ production ผ่าน UAT แล้ว

จอสาขาเปิดใช้งานแล้วแนวตั้ง/แนวนอน แบ่งหน้า เต็มจอ อ่านใหม่ทุก 15 วินาที

ระบบคู่แข่ง / สต็อก / POSยังไม่มีแยกเป็นงานอนาคต ไม่รวมใน MVP นี้

02 · กติกาธุรกิจและราคา

ระดับมูลค่าที่เรทฐาน SCBส่วนต่างรับซื้อส่วนต่างขาย
รายย่อย≤ 10,000 บาท0.80%0.80%
มาตรฐาน> 10,000 ถึง 50,000 บาท0.60%0.60%
ยอดใหญ่> 50,000 ถึง 200,000 บาท0.40%0.40%
ราคาพิเศษ> 200,000 บาท0.25%0.25%
ร้านรับซื้อ = SCB รับซื้อ × (1 − margin)
ร้านขาย = SCB ขาย × (1 + margin)

มุมมองฝั่งร้าน: รับซื้อคือ F → THB; ขายคือ THB → F ระดับราคาประเมินจากมูลค่าที่เรทฐานก่อนบวกส่วนต่าง ใช้ระดับเดียวทั้งรายการ รับซื้อปัดลง ขายปัดขึ้น ส่วนต่างยังไม่หักค่าธรรมเนียมและค่าใช้จ่าย จึงไม่ใช่กำไรสุทธิ

ฐานราคา: SCB เรทธนบัตรประกาศทั่วไป ไม่ใช่เรทคู่ค้าเฉพาะบัญชีหรือข้อมูล streaming ธนาคารอื่นและ BOT เป็นข้อมูลประกอบ ไม่แทนฐาน SCB โดยอัตโนมัติ

ต้องกำหนดก่อนเขียน pricing engine จริง: precision/step ของราคาและยอดเงินบาท, การประเมินรายการหลายสกุล และวิธีคำนวณเมื่อผู้ใช้ระบุยอด THB แทนจำนวนเงินต่างประเทศ ห้ามใช้ราคา mock เป็นเรทจริง
ตัวอย่างเพื่ออธิบายสูตรเท่านั้นก่อนปัดหมายเหตุ
SCB buy = 32; จำนวน 1,000 USDฐาน 32,000 บาท → มาตรฐาน → 32 × 0.994 = 31.808ไม่ใช่ข้อมูลราคาปัจจุบัน
SCB sell = 33; จำนวน 1,000 USDฐาน 33,000 บาท → มาตรฐาน → 33 × 1.006 = 33.198ผลสุดท้ายขึ้นกับ step ที่อนุมัติ

03 · โครงสร้างระบบ

แหล่งข้อมูล

SCB ประกาศธนบัตร → ตัวอ่านข้อมูล → ตรวจหน่วย/แถว/วันเวลา → snapshot ใหม่

บริการราคา

Server API + D1 → สูตรตามระดับ → manual override → ตรวจความขัดแย้ง → board state

ช่องทางใช้งาน

Telegram Bot / Mini App สำหรับเจ้าของ และจอสาขาแบบ read-only

ระบบอ้างอิง

11 ธนาคาร / BOT / Google Sheet แยกจากเส้นทางตั้งราคา SCB

เส้นทางความสัมพันธ์ข้อกำหนด
SCB → backendดึงและ normalize ก่อน commitsource failure เก็บ snapshot เดิมพร้อมคำเตือน
Mini App → backendตรวจ Telegram initData + ownerการเปลี่ยนข้อมูลผูก revision และยืนยัน
Telegram → webhooksecret header + allowlist + dedupคำสั่งเปลี่ยนต้อง /confirm
Backend → จอสาขาลิงก์อ่านอย่างเดียว 24 ชั่วโมงข้อมูล/API ต้องไม่เปิดเพียงเพราะเว็บไซต์ public
Scheduler → ตัวอ่านข้อมูลข้อเสนอ: งานทุก 15 นาทีฝั่งเซิร์ฟเวอร์ป้องกันงานซ้อน retry มีขอบเขต และบันทึกผล
Backend → Google Sheetข้อเสนอ: mirror/reportingกำหนด source of truth และห้าม sheet write ทับราคาโดยปริยาย
Rate API → XC Unifiedข้อเสนอ: adapter ใช้ service authquote เก็บ rate snapshot + tier + calculation version

Frontend ตามข้อมูลส่งต่อ: React / Vinext บน Sites; Backend: API ฝั่งเซิร์ฟเวอร์ + D1 ตารางหลักมี 4 ตาราง ด้าน XC Unified ใช้ฐานข้อมูลธุรกรรมอีกชุดหนึ่ง การเชื่อมต้องมีข้อตกลงผู้เป็นเจ้าของข้อมูลและสิทธิ์ API ก่อนลงมือ

06 · ลำดับงานและการควบคุมสถานะ

งานลำดับเงื่อนไขผ่าน
ตรวจ SCBfetch → parse → normalize → validate → คำนวณใหม่ → ตรวจ override → commit revision → auditไม่เขียน snapshot บางส่วนที่ตรวจไม่ผ่าน; เก็บเวลา source และเวลา fetch แยกกัน
เปลี่ยนราคาowner auth → validate payload → pending(base revision, expiry) → /confirm → revalidate → atomic commit → auditเจ้าของเดิม ภายใน 10 นาที และ revision ยังเดิม
ราคาปรับมือมี override → SCB ใหม่ → ตรวจความขัดแย้ง → valid หรือ hidden_conflictไม่ลบ override อัตโนมัติ; reset เท่านั้นที่ล้าง
จอสาขาสร้าง read-only link → ตรวจ token/expiry → poll 15s → render → next pageหมดอายุ/ไม่มีสิทธิ์/เชื่อมต่อไม่ได้ ซ่อนราคา
Scheduler · เสนอtick 15min → lock → refresh → บันทึกผล → sync sheet → releaseงานซ้อนถูกข้าม; sheet ล้มเหลวไม่ย้อนราคาที่ commit สำเร็จ
Unified quote · เสนอเลือกสกุล/ด้าน/จำนวน → base value → tier → rate snapshot → quote → transactionquote เก็บฐาน สูตร ราคาก่อน/หลังปัด และ expiry; ไม่เปลี่ยนเงียบเมื่อ SCB อัปเดต

Pending command: PENDING → APPLIED / EXPIRED / STALE / CANCELLED (ข้อเสนอชื่อสถานะ)
Override: ACTIVE ↔ HIDDEN_CONFLICT → RESET
Board: ACTIVE / PAUSED โดย source warning เป็นสถานะแยกจากการพักแสดงราคา

09 · API Contract และ Telegram

Endpoint ที่รายงานว่ามีหน้าที่สิทธิ์ / รูปแบบเสนอ
/api/ratesข้อมูลจอสาขาหรืออ่านเรทowner auth หรือ read-only board token ตาม route/mode; ต้องยืนยัน method ของจริง
/api/miniappข้อมูลและการกระทำใน Mini AppTelegram initData HMAC + owner + อายุ ≤24h; mutation ไม่ข้าม confirm
/api/refreshดึง SCB / อัปเดตฐานowner หรือ service credential ฝั่ง scheduler; idempotency/lock
/api/telegramWebhook Telegramsecret header + owner + chat allowlist + unique update_id

ข้อเสนอ payload อ่านราคา: revision, source{code,published_at,fetched_at,status}, paused, policy_version, tier_code, rows[{instrument_key,currency,banknote_band,display_multiplier,buy_thb_per_1,sell_thb_per_1,availability,override_status}] เก็บ rate เป็น decimal string หรือ null

ข้อเสนอ mutation: command_type, payload, expected_revision, request_id → คืน pending_id, expires_at, confirmation_instruction ยังไม่เปลี่ยน board จน confirm สำเร็จ ตรวจ state ใหม่ใน atomic transaction

คำสั่งประเภทผลที่ต้องได้
/help /rates /status /boardอ่านไม่เปลี่ยน state ราคา
/updaterefreshauth + lock + validation; ราคา SCB ใหม่อาจทำ override conflict
/price /margin /reset /pause /resumeเปลี่ยนข้อมูลสร้าง pending รอยืนยัน
/confirm รหัสยืนยันเจ้าของเดิม ภายใน 10 นาที revision ไม่เปลี่ยน ใช้ได้ครั้งเดียว
/update อาจเปลี่ยนราคาและ revision ได้ ต้องบันทึกใน audit แม้จัดอยู่ในคำสั่ง refresh และต้องยืนยันพฤติกรรมจริงว่า refresh ต้องใช้ confirm หรือไม่ ข้อมูลส่งต่อกำหนด confirm ชัดเจนสำหรับคำสั่งเปลี่ยน 5 รายการด้านบน

ข้อเสนอ error codes: UNAUTHORIZED, AUTH_EXPIRED, VERSION_CONFLICT, CONFIRM_EXPIRED, RATE_UNAVAILABLE, REFRESH_FAILED พร้อมข้อความภาษาไทยที่บอกวิธีแก้ ห้ามคืน stack trace หรือ secrets

11 · Acceptance Criteria และ UAT

กรณีผลที่คาดหวัง
ขอบเขต tier 10,000 / 50,000 / 200,000 และค่าที่สูงกว่าเล็กน้อยเลือก tier ตรงช่วงจากฐานก่อน margin ไม่วนเลือกจากราคาหลัง margin
สูตร buy/sell + rounding step ที่อนุมัติbuy ลง sell ขึ้น; Decimal ไม่คลาดเคลื่อนบริเวณขอบ
JPY/KRW และ USD หลายชนิดธนบัตรคำนวณต่อ1 แสดงตาม multiplier; ไม่มีคูณซ้ำ/ปะปน band
ไม่มีเรทบางด้าน / วันหยุดไม่แทน0 ใช้ประกาศล่าสุดพร้อมเวลาจริง
initData ปลอม / >24h / user อื่น / แชตไม่อนุญาตปฏิเสธ ไม่มี side effect
confirm คนอื่น / >10min / revision ใหม่ / รหัสใช้ซ้ำไม่ apply; ให้สร้างคำขอใหม่เมื่อ stale
webhook ซ้ำ / crash แล้ว retryไม่เปลี่ยนข้อมูลซ้ำ ตรวจการกู้ processing event ที่ค้าง
ปรับราคา → confirm → จอสาขาราคาเปลี่ยนตาม revision เดียว มี audit และหน่วยถูกต้อง
SCB ใหม่ขัด overrideoverride ยังอยู่ แต่ราคา conflict ซ่อนจนเจ้าของแก้/reset
source failure กับ screen connection failureกรณีแรกข้อมูลเดิม+คำเตือน; กรณีหลังซ่อนราคา
pause/resume / link24hไม่มีราคาเมื่อ paused/expired; resume ต้องสิทธิ์ครบ
scheduler ซ้อน / sheet ล้มเหลวไม่ commit ซ้ำ มีสถานะงาน; sheet ไม่ทำให้ราคาย้อนกลับ
quote snapshot · ระยะถัดไปราคาเดิมใน quote ไม่ถูก SCB ใหม่แก้เงียบ; expiry ต้อง requote

เจ้าของรายงานว่าตรวจสูตรราคา สิทธิ์เจ้าของ auth หมดอายุ/ปลอม confirm dedup และ API ปฏิเสธผู้ไม่มีสิทธิ์แล้ว และ webhook ไม่มี backlog/error ณ รอบเปิดใช้งาน ทีมพัฒนาควรแนบวันตรวจ commit/deployment revision และหลักฐานผลทดสอบจริง UAT ด้วย Telegram เจ้าของยังเป็นงานที่ต้องทำ

12 · แผนส่งมอบและจุดตัดสินใจ

ลำดับงานเสร็จเมื่อ
P0เทียบ schema/API จริงกับ blueprint และกำหนด rounding/conflict policyลงนาม contract, unit scale, precision และความหมายของ pause
